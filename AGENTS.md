# Repository Guidance

## Product

- The intended product is a multiplayer D&D application for the user and friends, with an AI model acting as Dungeon Master.
- The frontend stack is React with TanStack Router (code-based route tree in `apps/web/src/router.tsx`), shadcn/ui, and Tailwind CSS v4.
- Each player must be able to create and manage a character and assign that character to a campaign.
- The campaign must have persistent, structured state that the AI DM can read and update, including player characters, world progress, encounters, inventory, and other rules-relevant facts.
- Gameplay must follow the SRD turn structure; the DM chat must identify whose turn it is and suggest actions currently available to that character based on the authoritative game state and rules engine.
- The AI DM must use the SRD-backed rules engine and campaign state for adjudication; prompts alone must not be the authoritative source of rules or state.
- Treat `SRD_CC_v5.2.1.pdf` as the source of truth for supported 5.2.1 rules; do not silently substitute rules from another D&D edition or source.
- When implementing rules, prefer structured, testable game-state and rules-engine code over embedding rules only in prompts; the AI should narrate and adjudicate through those rules.
- Preserve the SRD's CC-BY-4.0 attribution in user-facing distribution or documentation: `This work includes material from the System Reference Document 5.2.1 ("SRD 5.2.1") by Wizards of the Coast LLC, available at https://www.dndbeyond.com/srd. The SRD 5.2.1 is licensed under the Creative Commons Attribution 4.0 International License, available at https://creativecommons.org/licenses/by/4.0/legalcode.`

## Architecture

- pnpm monorepo: `apps/web` (Vite + React frontend), `apps/server` (Hono + SQLite via Drizzle + better-sqlite3), `packages/shared` (domain types, the contract between frontend, backend, and rules engine).
- DB: SQLite file at `apps/server/data/domino.db` (gitignored), migrations in `apps/server/drizzle/`.
- Rules engine lives in `apps/server/src/rules/` (dice, abilities, combat, available actions, turn logic) and is the authoritative source for rules decisions — never let the AI model bypass it. Combat endpoints in `apps/server/src/routes/combat.ts` validate that attacks happen only on the current combatant's turn.
- AI DM lives in `apps/server/src/dm/`: `DM_TOOLS` (in `dm/types.ts`) defines the tool interface the model must use. `dmNarrate` calls an OpenAI-compatible LLM via `dm/llm.ts` — provider from `DM_PROVIDER` env: `deepseek` (default, needs `DEEPSEEK_API_KEY`), `groq` (free tier, `GROQ_API_KEY`), `openrouter` (`OPENROUTER_API_KEY`, `:free` models), or local `ollama` (no key, `ollama pull qwen3:8b`). Model via `DM_MODEL`. Without the right key, chat returns a canned "DM preview" reply. Tools (`tools.ts`) read/write campaign state through `apps/server/src/campaign/store.ts` (single place that persists state and emits `game_events`).
- Combat is handled by REST endpoints under `/api/campaigns/:id/combat` (generate/start/advance/end/attack/death-save); there is no WebSocket/SSE yet — other players see changes after refresh. Encounters are always generated by the DM, never entered by hand and there is no button for it: the AI calls the `generate_encounter` tool when the plot demands it, and in preview mode (no LLM key) the narrator auto-starts an encounter when a player message carries combat intent. `POST /combat/generate` (and the tool) match the threat description against the SRD monster catalog in `apps/server/src/rules/monsters.ts` and scale counts to party size.
- Demo data: `pnpm --filter @domino/server db:seed` creates user `demo`/`demo1234` with a Cleric and a campaign (skips if DB is not empty).
- Auth: sessions in SQLite via httpOnly cookie (`session`). Client calls go through Vite proxy `/api` -> `http://localhost:3001` (server port 3001).
- Shared types must stay in sync between server routes and web pages; run `typecheck` after changing them.

## Commands (run from repo root)

- `pnpm dev` — server (tsx watch, port 3001) + web (vite, port 5173) with concurrently.
- `pnpm build` — tsc build of server, `tsc --noEmit && vite build` of web.
- `pnpm typecheck` — all packages (run after any shared-type change).
- `pnpm test` — vitest in server (rules engine tests in `apps/server/src/rules/rules.test.ts`).
- `pnpm lint` — eslint (flat config at repo root).
- `pnpm db:generate` — drizzle-kit migrations from `apps/server/src/db/schema.ts`.
- `pnpm db:migrate` — apply migrations (also needed after fresh clone; server does not auto-migrate).
- `pnpm --filter @domino/server db:seed` — demo user/campaign (skips if DB non-empty).

## Gotchas

- Server reads `.env` from `apps/server/.env` (`--env-file`); copy `.env.example` before first run.
- `pnpm.onlyBuiltDependencies` in root `package.json` allows `better-sqlite3`/`esbuild` postinstall scripts — do not remove, or native builds silently break.
- TypeScript is pinned to `~5.9.3` for typescript-eslint compatibility; don't bump to 7.x blindly.
- Server uses `tsx` at runtime (no build step in dev); production start requires `pnpm build && pnpm start` in `apps/server`.
- Web pages use `useAuth` for the current user; `apps/web/src/router.tsx` guards `/app/*` routes render-side.
